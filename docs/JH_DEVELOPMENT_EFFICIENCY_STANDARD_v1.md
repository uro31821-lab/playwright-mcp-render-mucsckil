# JH 개발 효율 운영 기준 v1

## 목적
JH 개발에서 같은 설명·조사·설치·검증을 반복하지 않고, 현재 목표에 필요한 다음 단계만 수행한다. 기존 jh-dev-toolkit, jh-operational-learning, Secure/Secure56, Android 승인·no-replay 규칙을 대체하지 않고 그 위에 적용하는 효율 기준이다.

## 1. 마스터 지침 재사용
- 앱 ID·패키지명·원본 인증서·Java/Gradle/SDK·Secure56·승인/no-replay·원클릭 ZIP·검증 단계는 최신 확정 기준을 재사용한다.
- 현재 사용자의 최신 지시와 현재 프로젝트 원본이 과거 지침보다 우선한다.
- 한 작업 전용 예외를 전역 규칙으로 승격하지 않는다.
- 시작 순서: 목표/원본 확인 → 관련 지침만 읽기 → 해결 기록/최근 체크포인트 조회 → 완료/미완료 분리 → 다음 미완료 단계 실행.

사용자 표시 기본형:
- 현재 단계
- 이미 확인
- 막힌 이유
- 다음 행동

## 2. 새 대화 전환 기준
다음 중 하나가 생기면 체크포인트로 새 대화에 인계한다.
- 목표 또는 모듈이 크게 바뀜
- 같은 설명·질문·진단이 반복됨
- 오래된 실패와 현재 결과가 섞임
- 다음 미완료 단계 식별이 불안정해짐
- 여러 독립 작업의 승인·결과·원본이 섞일 위험이 있음

### 인계 7항목
1. 목표
2. 정확한 원본(repo/branch/commit/version/대상)
3. 완료 + 근거
4. 실패 원인(확인/미확인 구분)
5. 반복 금지
6. 남은 검증
7. 다음 한 행동

긴 대화 전체를 복사하지 않고 RESULT·로그·receipt·파일·커밋을 참조한다.

## 3. 해결 기록 구조화
실제 해결·검증 후 다음을 기록한다.
- 증상
- 원인
- 해결
- 검증 근거
- 재사용 조건
- 재사용 금지 조건
- 마지막 확인일

같은 증상이 나오면 새 검색·새 설치·새 추측 전에 기존 검증 기록을 먼저 찾는다. 조건이 같으면 재사용하고, 다르면 달라진 부분만 새로 검사한다.

## 4. 토큰·시간 절약
- 현재 대화에 있는 정보를 다시 검색하지 않는다.
- 이미 선택한 옵션을 다시 묻지 않는다.
- 유효한 빌드·서명·APK·테스트 결과는 조건이 같으면 재사용한다.
- 영향이 작은 변경에 무조건 전체 검사를 반복하지 않는다.
- 공통 계약·라우터·보안 경계 변경은 필요한 전체 회귀를 생략하지 않는다.
- 실패가 명확하면 같은 방법을 반복하지 않고 원인을 수정한 뒤 검증한다.
- 사용자에게 내부 로그를 길게 보여주지 않고 결론과 다음 행동을 먼저 보여준다.

## 5. 기존 JH 연결
- 상세 개발/검증/빌드/ZIP: jh-dev-toolkit
- 오류·성공·검증된 교훈: jh-operational-learning
- 비서별 운영·실사용 검증: jh-assistant-ops-board
- 보안·승인·기기 실행: 기존 Secure/Secure56 및 Android 규칙

새 인증서·새 APK·새 서버·새 저장소·새 메모 시스템을 이 기준 때문에 만들지 않는다.

## 완료 판정
이 기준 저장만으로 현재 작업이나 기존 모든 대화가 자동 갱신됐다고 말하지 않는다. 실제 빌드·서명·설치·E2E·외부 실행 여부는 각각 별도 확인한다.
