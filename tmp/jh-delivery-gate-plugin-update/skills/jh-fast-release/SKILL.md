# JH 빠른 개발·1회 최종 기기 검증 — 2026-10-30

모든 JH 개발에서 [현재 개발도구](../jh-dev-toolkit/SKILL.md)의 진행·회귀·도구 보관·검증 후보를 우선하고, 아래 경로를 **지체 없이 적용**한다. 이 파일은 휴대폰 승인/기기 실행/서명 규칙을 대체하거나 필수 회귀를 생략하는 면허가 아니다.

## 공통 규칙과 전달 세부 계약

[통합 작업 규칙](../jh-dev-toolkit/references/shared-work-rules.md)의 R01–R14를 적용한다. 실제 시작·완료 경로, 검사 선택, 결과 재사용, CI와 인계는 [개발 진행 기준](../jh-dev-toolkit/references/development-flow.md)과 [회귀검사 기준](../jh-dev-toolkit/references/regression-policy.md)에 모았다. 구조 분석에는 [REA 실행기](../jh-rea-executor/SKILL.md)의 저장 결과를 먼저 사용한다.

Windows 사용자 전달물은 [압축 풀기 → 실행.cmd 세부 계약](references/unzip-run.md)을 적용하고 현재 toolkit의 포장 게이트를 통과시킨다. **사용자에게 실제 파일 링크를 보여주기 전에는 에비서의 [파일 전달 게이트](../jh-ebiseo-assist/references/file-delivery-gate.md)도 반드시 통과한다. ZIP 내부 무결성 PASS와 사용자 전달 준비 PASS를 같은 상태로 보지 않는다.** 이 스킬은 아래의 출시 분기·후보·최종 기기 세션에 집중한다. `1회`는 불필요한 반복을 줄이는 목표이며 필요한 재검증을 금지하는 제한이 아니다.

## 목표와 실행 순서

`기존 마지막 완료 지점 확인 → 소스 차이 분류 → 서버/호스트 비기기 경로 연결·검사 → 정확한 출시 후보 동결 → 기존 서명 APK 재사용 또는 변경 시 1회 빌드·서명 → 사용자 승인 업데이트 설치 → 한 세션에서 기기 종단검증 → 증거 저장`.

실기기가 필요 없는 연결 계약·모듈 구현·네이티브 어댑터 주입·정적 검증·개발 브랜치 CI를 **실기기 시험보다 먼저** 처리한다. 하지만 기기에서만 확인 가능한 승인을 가짜 테스트·서버 성공으로 대체하지 않는다. 이미 설치된 앱/운영 호스트와 후보가 불일치하면 배포하지 말고 영향 범위를 확인한다. 기존 소스와 앱이 바뀌지 않았으면 APK를 다시 만들지 않는다.

## 작업 분기

- **코드 변경 없음·기준 증거 일치:** Gradle/CI/서명 반복하지 않는다. 다음 미완료 작업만 수행한다.
- **서버/Node만 변경:** 영향 범위 검사 및 필요한 CI를 한 번 확인한다. Android 소스·앱 ID·서명·빌드 입력이 그대로면 APK 재빌드·휴대폰 재설치하지 않는다. 운영 배포 승인은 별도 보존한다.
- **Android 소스/Manifest/의존성 변경:** 마지막 검증 후보 대비 미검증 차이만 검토하고 해당 회귀 및 전체 필수 Android 게이트 수행; 이전 검증된 Gradle/SDK/서명키와 빌드 캐시 재사용. 확정 후보에서만 다시 빌드·서명한다.
- **공통 Secure56, 권한, 작업 ID, 서명/영수증, 공통 런타임 변경:** 양쪽 구현과 고정 벡터·승인/재실행 방지·전체 영향 회귀/통합검사 완료 후 한 번의 통합 후보 생성. 기존 권한 우회 금지.
- **설치·UI 검증만 남음:** 이미 보관된 해당 후보의 서명 APK 재사용. 연결되지 않은 JH BEGIN_COMMAND, 새 승인, 재열기 요청을 진단용으로 만들지 않는다.

중복 실행하지 않는다는 뜻은 **동일한 소스·도구·빌드 설정·테스트·환경·서명키·체결된 승인**의 증거가 여전히 유효하다는 뜻이다. 조건이 바뀌거나 검증이 빠졌으면 필요한 부분은 다시 검사한다. 캐시/CI 성공과 현장 동작 확인은 다르다.

## 사용자 조작을 한 세션으로 압축

실기기 전에 현재 완료 기록·체크포인트·APK 파일/해시·앱 버전/서명·서버 branch/CI/run/환경을 먼저 확인한다. 원격 설치 자동실행과 운영 배포를 승인된 것으로 간주하지 않는다. 기존 앱 데이터 유지 가능한 `업데이트 설치` 경로만 택하고, 앱 삭제·데이터 초기화·서명키 교체 금지. 버전/서명 충돌 시 설치를 멈춘다.

휴대폰 준비와 해당 작업의 실제 승인이 유효하면 **하나의 기기 검증 세션**에서 현재 요청에 해당하는 시나리오와 결과 회수를 확인한다. 아래 목록은 JH168 Gemini 3기능 후보의 예시이며 일반 JH 작업에 Gemini 화면 배치나 세 기능 검증을 강제하지 않는다. 다른 작업은 현재 선택한 앱·창·엔진과 목표를 기준으로 한다. 기기 명령은 실제 원본 Secure56 서명·승인·작업 바인딩을 따라야 하고 각 외부효과는 새 요청별 독립 승인·결과 조회를 지킨다.

1. 설치된 버전/서명 및 GPT 왼쪽·Gemini 오른쪽의 실제 앱·창 바인딩 확인.
2. Android 단일 안전 조작: 정확한 화면/명령/승인 경계 및 완료 영수증 확인.
3. 유튜브 요약: 요청/원문 근거/동일 작업 답변 귀속/ChatGPT 결과 확인.
4. 영상 제작: 생성/파일 보관/검증된 재생 링크 또는 전달 결과/ChatGPT 반환을 확인; 실제 외부 파일은 별도 보안 경계 유지.
5. 공통 Secure56: 중복 제출 0, 승인 재질문 불필요 0, 미확정 실행 자동 재시도 0, 취소·만료·오류 시 거부와 원인 보고 확인.

실제 자동화로 검증된 동작은 반복 클릭하지 않는다. 오직 다음 관찰에 필요한 최소 사용자 동작만 안내한다. 한 번의 세션에서 가능한 단계들을 묶되, 서로 다른 외부효과를 '1개 명령 승인'으로 합치지 않는다. 오류가 나면 **기존 실행 영수증부터 조회**, 결과 미확정이면 재시도하지 않고 해당 단계에서 멈춘다. 수정 후에는 영향받은 부분만 재검증하고 공통 게이트는 마지막 검증 조합에서 확인한다.

## 실제 사용

현재 실행환경에서 접근 가능한 JH source, GitHub/CI, 플러그인 소스, 파일 보관 증거를 **선택적으로 읽고 바로 구현**한다. 단순 상태 확인은 JH `life_status` 등 읽기 전용만; 개발 전용으로 `BEGIN_COMMAND` 만들지 않는다. 계정·Primary·방법 승인·운영 서버·프라이빗 소스 공유 여부는 기존 범위대로 유지한다. 필요한 사용자 작업이 없으면 사용자를 끌어들이지 않는다. 마무리에서 증거 없는 설치/배포 성공 주장 금지.
