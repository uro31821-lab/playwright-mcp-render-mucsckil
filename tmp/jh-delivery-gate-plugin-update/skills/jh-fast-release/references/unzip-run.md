# JH Windows 배포 표준: 압축 풀기 → 실행.cmd

확정일: 2026-10-30. 사용자용 JH 빌드·업데이트·검증 ZIP에 공통 적용한다. Perplexity 근거 검색, 이비서, 카비서, Gemini와 후속 기능도 예외로 다른 실행 절차를 만들지 않는다. 소스 참고본·도구 보관본은 실행용 배포본과 구분한다. 이 문서 저장은 실행기 구현·Windows 실행·APK 설치 완료의 증거가 아니다.

## 1. 사용자가 기억할 동작은 하나

**Windows PC에서 ZIP 전체 압축 풀기 → 압축 해제 폴더의 실행.cmd 더블클릭.**

- 실행 파일 이름은 항상 `실행.cmd`이며 버전·기능 이름을 붙이지 않는다. ZIP 이름에는 버전·대상을 표시할 수 있지만 실행 동작은 바꾸지 않는다.
- 첫 화면에 사용자가 선택해야 할 실행 파일을 여러 개 놓지 않는다. `START...cmd`, `BUILD...cmd`, `APK-ONLY.cmd`, `.ps1` 등 기존 실행기는 내부에서 재사용한다. 옮길 경우 상대경로와 호출자를 함께 수정·확인한다. 파일 이름만 바꾸고 동작 검증 없이 완성본으로 제공하지 않는다.
- 사용자가 소스 복사·파일별 병합·경로 수정·명령어 입력·추가 ZIP 압축 해제·여러 실행 파일 선택을 하도록 요구하지 않는다. 파일 확장자 숨김 환경에서도 누를 파일을 알아볼 수 있게 안내한다.
- `실행.cmd`는 PC 실행용이다. 휴대폰에서 CMD를 실행하라고 안내하지 않는다. 휴대폰 설치·권한·로그인 등 실제 사용자 승인은 별도 필수 단계로 정확히 안내하며, 이를 몰래 자동 승인하거나 두 단계만으로 모든 외부 작업이 끝난다고 약속하지 않는다.

## 2. 외형과 결과 위치 고정

```text
압축 해제 폴더/
  실행.cmd          # 유일한 사용자 실행 진입점
  사용안내.txt       # 대상, 실행 방법, 필요한 실제 승인만
  data/             # 내부 실행기·검증된 소스/변경분/산출물·manifest
  RESULT.txt        # 실행 시 생성하는 결과 요약
  logs/             # 실행 시 생성하는 상세 로그
```

위 구조는 전달용 외형이다. 내부 프로젝트의 기존 레이아웃을 불필요하게 재작성하지 않는다. 내부 호출은 실행기 자신의 위치를 기준으로 절대경로/따옴표를 사용하고 현재 작업 폴더에 의존하지 않는다. 알려진 짧은 빌드 작업 경로가 필요하면 실행기가 안전하게 준비하며 사용자가 폴더를 옮기도록 하지 않는다. 개인키·암호·API 키·토큰을 배포 ZIP이나 로그에 넣지 않는다.

## 3. 본체 하나에 기능 변경분을 누적

- 배포 전 개발자가 현재의 최신 JH 기준 소스에 필요한 모듈 변경분을 병합·검증한다. 각 개발방의 오래된 JH 전체 ZIP을 차례로 설치하거나 최신 본체 위에 통째로 덮어쓰지 않는다. Gemini 등 이후 변경을 보존한다.
- 준비된 Android 변경은 가능한 한 한 통합 후보로 묶는다. 서버 전용 변경을 위해 APK를 만들지 않으며, 미완성 기능 하나 때문에 독립적으로 준비된 기능을 무기한 묶지 않는다.
- 런타임 패치가 필요한 경우에는 명시된 호환 기준과 허용 경로만 적용한다. 원본 불일치·사용자 변경·여러 기준본이 발견되면 무조건 덮어쓰거나 해시 검사를 끄지 않는다. 안전하게 중단하고 원인 및 필요한 한 가지 조치를 알린다. 수동 소스 병합을 사용자에게 넘기지 않는다.
- 이름·날짜·파일 수만으로 최신 여부를 판단하지 않는다. 프로젝트, 소스/산출물 식별자, 앱 ID·버전·기존 인증서, 모듈/서버 계약을 필요한 범위에서 대조한다. 기록된 경로는 현재 환경에서 접근·실행 가능해야 재사용한다.

## 4. 같은 버튼 안에서 필요한 일만 선택

| 패키지/상태 | 실행기가 수행할 범위 |
| --- | --- |
| 서버·근거 검색 연결만 변경 | 해당 서버 후보·설정·검사/결과만 처리. Android SDK 탐색·빌드·서명·휴대폰 설치는 하지 않음. 운영 변경은 유효한 승인 경계 유지. |
| 소스에 맞는 검증된 서명 APK 보유 | 유효한 검증 증거를 재사용하고 산출물 제공 및 필요한 업데이트 안내로 진행. 같은 APK를 만들기 위해 재빌드·재서명하지 않음. |
| 실제 Android 변경으로 새 빌드 필요 | 프로젝트에 맞는 기존 SDK·JDK·Gradle·캐시·원래 서명을 재사용해 필요한 빌드/검사만 실행. 새로운 서명키 생성·무조건 clean/재설치 금지. |
| 같은 입력의 준비 작업 이미 완료 | 완료 결과를 표시하고 다음 미완료 단계만 제시. 기존 결과를 새 실행 성공으로 집계하지 않음. |
| 빌드는 성공하고 결과 복사/회수만 실패 | 보존한 종료 코드·APK·로그로 회수 단계만 재개. 빌드·시험·서명부터 다시 하지 않음. |
| 원본·서명·버전 충돌 또는 필수 자료 없음 | 실제 차단 사유와 필요한 한 가지 조치 표시. 구버전 강제 덮어쓰기·앱 삭제·데이터 초기화 금지. |

패키지에 고정된 작업 종류를 manifest에서 읽어 기본 동작을 정한다. 사용자가 빌드/설치/복구/서버 스크립트 중 하나를 매번 골라야 하는 메뉴를 기본으로 만들지 않는다. 기존 서명키와 보안 설정은 원래 저장 위치에서 사용하며 채팅에 키·암호를 제출하도록 요구하지 않는다. 소스에 맞는 APK가 있으면 SDK 부재만으로 처음부터 환경을 설치하지 않는다.

## 5. 재실행·실패도 같은 진입점

- 같은 `실행.cmd`를 다시 누르면 저장된 입력·후보·결과를 대조해 완료된 준비 작업을 재사용한다. 입력이나 조건이 바뀐 검사만 갱신한다.
- 중복 클릭은 진행 중 실행으로 안내하고 같은 빌드·서명·설치를 병렬 시작하지 않는다. 진행 중인 원래 프로세스를 임의로 종료하지 않는다.
- 설치·배포·전송 등 외부 효과의 결과가 불명확하면 영수증/실제 상태를 먼저 확인한다. 재클릭이 자동 재설치·재배포·재전송의 허가가 아니다. 이전 실행이나 오래된 승인 기록을 새 작업 승인으로 쓰지 않는다.
- 오류가 나면 실제 실패 단계에서 멈추고 로그를 남긴다. 실행 창이 설명 없이 사라지지 않게 한다. 이미 완료된 작업과 미완료 작업을 분리하고 무한 재시도하지 않는다.

## 6. 진행·결과를 같은 방식으로 표시

실행 중 현재 단계·마지막 활동 시각을 화면과 로그에 함께 표시한다. 정상 종료든 실패든 `RESULT.txt`에 후보/패키지 ID, 작업 종류, 단계별 실행/재사용 상태, 종료 코드, 최초 실패 원인, 산출물 및 로그 위치, 다음 필요한 사용자 동작을 기록한다. 정상 경로에서는 결과 요약과 산출물 위치를 바로 보여 준다.

상태는 `REUSED_PASS`, `NEW_PASS`, `NOT_RUN`, `BLOCKED`, `FAILED`와 실제 사용자 승인 대기를 구분한다. 빌드·서명·설치·실기기 기능 확인·운영 배포는 별도 항목이다. `APK 준비 완료`를 `휴대폰 설치 완료`로 바꾸지 않는다. 민감정보와 개인 화면/요청 본문을 로그에 저장하지 않는다.

## 7. 배포 전에 실행 진입점까지 검증

현재 프로젝트의 기존 실행기를 재사용하고 변경된 포장/호출부에 필요한 검사만 수행한다. 압축 해제된 실제 ZIP의 첫 실행, 공백·한글 경로, 실패 시 결과 저장, 재실행 시 완료 단계 재사용, 중복 실행 방지, 이전 본체 보호, 실제 payload 연결을 확인한다. 한글 경로 문제가 입증된 도구는 기존 성공 작업 경로를 재사용한다.

Windows 실행 환경에서 수행하지 못한 검사는 `NOT_RUN`으로 남긴다. 정적 검사·ZIP 내용 확인만으로 Windows 실행 통과를 주장하지 않는다. 실행기가 안내문만 띄우거나 payload/연결부가 없으면 설치용 완성본으로 내보내지 않는다. 원클릭 외형을 이유로 OS 보안 설정·권한·서명 검증을 우회하지 않는다.

이 기준은 이후 전달할 실행용 ZIP을 위한 포장 규칙이다. 기존에 검증·보관된 모든 ZIP/APK를 이 문서 추가만을 이유로 다시 만들지 않는다. 실제 전달/수정 시 필요한 패키지에만 적용하고 그 결과를 확인한다.


## 8. 사용자 다운로드 링크를 만들기 전 전달 게이트

Windows 실행 ZIP도 내부 포장 검사만 끝났다고 바로 링크하지 않는다. 에비서의 [파일 전달 게이트](../../jh-ebiseo-assist/references/file-delivery-gate.md)를 추가로 통과해야 한다.

- 실제 사용자 전달 경로에 있는 최종 ZIP의 존재·크기·SHA-256을 확인한다.
- ZIP을 다시 열어 CRC/entry readback과 약속한 진입점 존재를 확인한다.
- `실행.cmd`는 Windows CRLF와 약속한 인코딩을 확인하고, PowerShell 5.1 스크립트는 single UTF-8 BOM + CRLF인지 확인해 double BOM을 차단한다.
- 기본 다운로드 파일명은 짧은 ASCII 이름을 우선한다.
- 정확한 sandbox/container 경로가 현재 런타임에서 확인되지 않았으면 다운로드 링크를 만들지 않는다.
- opaque file id나 내부 업로드 성공은 사용자 다운로드 성공이 아니다.
- 링크 실패 보고가 오면 같은 유효 ZIP 바이트를 새 짧은 이름으로 재전달하고 해시를 비교한다. 소스·Gradle·서명은 그 이유만으로 반복하지 않는다.
- 최종 보고에는 `DELIVERY_GATE_PASS`와 `USER_DOWNLOAD_CONFIRMED`를 별도 상태로 둔다.
